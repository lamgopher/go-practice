## Практика

Постройте систему с воркшопа, но доведите её до состояния, в котором саги не теряются и наблюдаемы.
Монорепозиторий:

```
proto/            order.proto → общий модуль с типами событий
pkg/kafka/        обёртки над sarama: consumer group + sync producer
orders/           сервис заказов
warehouse/        склад (резерв)
catalog/          проверка стоимости
shipping/         проверка доставки
client/           генератор заказов
docker-compose.yml  Kafka, Kafka UI, PostgreSQL
```

### Шаг 1. Проектирование на бумаге

1. Нарисуйте автомат состояний заказа: `NEW → PRICE_CHECKED → SHIPPING_CHECKED → RESERVED → COMMITTED`, ветви в
   `CANCELLED` из каждого промежуточного состояния.
2. Таблица шагов саги «создание заказа»:

   | Шаг | Сервис | Локальная транзакция | Компенсация | Тип |
   |-----|--------|----------------------|-------------|-----|
   | 1 | orders | сохранить заказ | отменить заказ | ? |
   | 2 | catalog | проверить стоимость | — | ? |
   | 3 | shipping | проверить доставку | — | ? |
   | 4 | warehouse | зарезервировать товары | снять резерв | ? |
   | 5 | orders | подтвердить заказ | — | ? |

3. Схема хореографии: для каждого топика — кто пишет, кто читает (с именем consumer group). Имена событий — в
   прошедшем времени: `order_created`, `price_confirmed`, `shipping_confirmed`, `products_reserved`,
   `order_committed`, `order_cancelled` (с причиной и шагом).
4. Спроектируйте (без реализации) саги «оплата» и «отмена оплаченного заказа».

### Шаг 2. Каркас

1. `order.proto`: `Order{id, user_id, items[], status}`, событие-обёртка `OrderEvent{event_id, saga_id, type, order, reason, occurred_at}`.
2. `pkg/kafka`: `Consume(ctx, cfg, topic, group, func(ctx, *sarama.ConsumerMessage) error)` и синхронный продюсер.
   Никакого busy loop: блокирующее чтение из claim, выход по контексту.
3. docker-compose и Makefile (`up`, `gen`, `run-all`).

### Шаг 3. Счастливый путь

1. `client` раз в секунду публикует `order_created` (ключ = id заказа), иногда — с уже использованным id.
2. `orders` сохраняет заказ (сначала в памяти под мьютексом), повторное создание игнорирует.
3. `catalog`, `shipping`, `warehouse` обрабатывают свои события и публикуют следующие.
4. `orders` по `products_reserved` переводит заказ в `COMMITTED`.
5. Проследите один заказ по всем топикам в Kafka UI (`kcat` с декодированием protobuf или UI с поддержкой protobuf).

### Шаг 4. Отказы и компенсации

1. Каждый сервис с вероятностью 10% (настраивается) отвечает отказом и публикует `order_cancelled{step, reason}`.
2. `orders` по `order_cancelled` переводит заказ в `CANCELLED`; `warehouse` (отдельная group) снимает резерв, если он был.
3. Компенсации идемпотентны: повторная отмена и отмена незарезервированного заказа — не ошибка.
4. Отказ после поворотной точки невозможен: `orders` обязан довести подтверждение до конца, повторяя попытки.
5. Соберите статистику за 1000 заказов: сколько подтверждено, сколько отменено на каждом шаге; сверьте с остатками
   на складе — «утёкших» резервов быть не должно.

### Шаг 5. Надёжность

1. Замените in-memory хранилища на PostgreSQL. Запись состояния и публикация события — через transactional outbox
   (занятие 14) и ретранслятор (занятие 19).
2. Идемпотентность потребителей: таблица обработанных `event_id` в той же транзакции, что и изменение состояния.
3. Убивайте сервисы `kill -9` в случайные моменты под нагрузкой (скрипт хаоса). Инвариант после остановки нагрузки
   и «успокоения» системы: нет заказов в промежуточных состояниях; сумма резервов равна сумме по подтверждённым заказам.
4. «Застрявшие» саги: фоновый процесс находит заказы, пробывшие в промежуточном состоянии дольше N минут, и
   отменяет их (таймаут саги). Что будет, если запоздавшее событие придёт после отмены по таймауту?
5. Несъедобное сообщение не должно блокировать партицию: dead-letter-топик.

### Шаг 6. Изоляция

1. На складе 1 единица товара; запустите 20 одновременных заказов на него. Подтверждён должен быть ровно один.
2. Реализуйте резерв атомарно: `UPDATE stock SET reserved = reserved + $n WHERE product_id = $1 AND total - reserved >= $n`.
3. Заказ в состоянии `NEW` виден пользователю как существующий, хотя может быть отменён. Какие контрмеры
   («семантическая блокировка», статус «в обработке») уместны? Реализуйте одну.

### Шаг 7. Наблюдаемость

1. `saga_id` (он же id заказа) и `trace_id` в заголовках всех сообщений и во всех логах.
2. Сквозной трейс одного заказа через все сервисы и топики.
3. Метрики: начато/подтверждено/отменено саг (с лейблом шага отмены), длительность саги (гистограмма), число саг
   в промежуточных состояниях (gauge), lag по группам.
4. Дашборд «воронка саги» и алерт на рост застрявших саг.

### Шаг 8. Оркестрация

1. Перепишите ту же сагу в виде оркестратора: сервис `order-saga` хранит состояние саги в таблице, отправляет
   команды (`reserve_products`) и ждёт ответы (`products_reserved` / `reserve_failed`); шаги описаны декларативно
   (список «действие + компенсация»).
2. Сравните с хореографией: где видна вся сага; сколько сервисов знают о саге; как добавить шаг; что происходит при
   недоступности оркестратора; как устроено тестирование.
3. Unit-тесты автомата оркестратора: успех, отказ на каждом шаге, повтор ответа, ответ не по порядку.

## Критерии готовности

- После хаос-прогона инварианты целостности выполняются; дубли и повторы не ломают состояние.
- Для любого заказа за минуту отвечаете, на каком шаге он находится и почему отменён.
- Можете аргументированно выбрать хореографию или оркестрацию для новой задачи.
- Понимаете, какие гарантии сага даёт (атомарность через компенсации, согласованность в конечном счёте) и каких не
  даёт (изоляция).
