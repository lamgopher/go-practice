## Вопросы для самопроверки

1. На какие четыре вопроса отвечает метаинформация коммита?
2. Почему Git называют распределённой системой и что в этой схеме означает «источник правды»?
3. Чем отличаются состояния файла untracked, modified и staged? Что будет, если выполнить `git commit` при пустом staging?
4. Что показывает `git status`, а что `git log`? Что покажет `git log` в только что созданном репозитории?
5. Что такое `HEAD`? Что такое состояние `detached HEAD` и почему в нём не стоит делать коммиты?
6. Что физически происходит при `git branch second`? Меняется ли что-то в файлах?
7. Чем `git checkout -b third` отличается от `git branch third`?
8. Чем результат `git merge` отличается от `git rebase`, если ветки разошлись? Что рекомендовал лектор по умолчанию и когда уместен merge?
9. Чем `git pull` отличается от `git pull --rebase`?
10. Когда возникает конфликт? Назовите три стратегии его разрешения.
11. Чем `git revert` лучше удаления коммита из истории общей ветки?
12. Для чего нужен `git cherry-pick`? Приведите жизненный пример.
13. Какие файлы не должны попадать в репозиторий и как это обеспечить?
14. Сравните три стратегии ветвления: долгоживущие ветки, одноразовые ветки, trunk-based. Когда какая подходит?

## Практика

Всё делается в пустой папке, например `~/git-review`. После каждого шага смотрите `git status` и
`git log --graph --decorate --oneline --all` и проговаривайте, что изменилось.

### Задание 1. Три коммита (повтор примера лектора)

1. Создайте `my_module.py` с двумя строками:
   ```python
   def my_function(a, b):
       return a * b + 10
   ```
2. `git init`, посмотрите `ls -la` и содержимое `.git`. Выполните `git log` и `git status` — объясните вывод.
3. Проверьте `git config --global user.name` и `user.email`; задайте, если пусто.
4. Сделайте коммит `initial commit`. Найдите его хеш, выполните `git show <hash>`.
5. Добавьте вторую функцию, посмотрите `git diff`, сделайте второй коммит.
6. Добавьте три строки комментария сверху и замените тело первой функции на `return a + b`. Перед коммитом
   объясните, почему в `git diff` одна строка красная и одна зелёная.
7. Попробуйте закоммитить, не выполнив `git add`. Что произошло и почему?

Проверка: `git log --oneline` показывает три коммита.

### Задание 2. Путешествие по истории

1. Перейдите `git checkout <хеш первого коммита>`. Прочитайте сообщение целиком. Откройте файл.
2. Вернитесь `git checkout master` (или `git switch -`).
3. Повторите для второго коммита через `git switch --detach <hash>`.
4. Ответьте письменно: к чему был бы «прикреплён» коммит, сделанный в этом состоянии?

### Задание 3. Удалённый репозиторий

1. Создайте пустой репозиторий на GitHub/GitLab, выполните `git remote add origin <url>`, проверьте `git remote -v`.
2. `git push origin master`.
3. В веб-интерфейсе откройте Blame для файла — сопоставьте строки с тремя коммитами.
4. Через веб-интерфейс добавьте `new_module.py` коммитом в master.
5. Локально: `git log` (нового коммита нет — почему?), затем `git pull origin master`.
6. Склонируйте репозиторий в соседнюю папку `git clone <url>` и проверьте, что `origin` уже настроен.

### Задание 4. `.gitignore`

1. Создайте `build/out.bin`, `.DS_Store`, `__pycache__/x.pyc`. Убедитесь, что `git status` их видит.
2. Напишите `.gitignore`, после которого `git status` показывает только сам `.gitignore`.
3. Усложнение: файл `secret.env` уже закоммичен. Как сделать, чтобы Git перестал его отслеживать, не удаляя с диска?

### Задание 5. Ветки, merge и rebase

1. `git branch second`, затем `git checkout second`. Добавьте функцию `new_function`, закоммитьте.
2. Вернитесь в master, убедитесь, что функции там нет. Поменяйте тело первой функции на `return 5`, закоммитьте.
3. Нарисуйте граф на бумаге, потом сверьтесь с `git log --graph --decorate --oneline --all`.
4. Сохраните состояние: `git branch backup-master master`.
5. Вариант А: `git merge second -m "merging second into master"`. Посмотрите граф.
6. Откатитесь: `git reset --hard backup-master`. Вариант Б: `git rebase second`. Посмотрите граф.
7. Сформулируйте разницу графов одной фразой.

### Задание 6. Конфликт

1. `git checkout -b third`, в первой функции сделайте `return 5 + 1`, закоммитьте.
2. В master в той же строке сделайте `return 5 - 2`, закоммитьте.
3. `git merge third` — получите `CONFLICT`. Откройте файл, найдите три маркера и объясните, что между ними.
4. Разрешите конфликт как на лекции (`return 5 - 2 + 1`), `git add`, `git commit`.
5. Повторите сценарий заново и разрешите его двумя другими стратегиями: целиком своё (`git checkout --ours`) и
   целиком чужое (`git checkout --theirs`).
6. Повторите сценарий с `git rebase third` вместо merge. Чем отличается порядок действий (`git rebase --continue`)?

### Задание 7. cherry-pick, revert, amend

1. В ветке `feature` сделайте три коммита в три разных файла. Перенесите в master только второй: `git cherry-pick <hash>`.
2. Отмените его через `git revert <hash>`. Посмотрите историю: сколько стало коммитов и почему это лучше удаления?
3. Сделайте коммит, «забыв» про файл `README.md`. Допишите его в тот же коммит через `git commit --amend`.
   Сравните хеш до и после. Почему так нельзя делать с уже запушенными коммитами?

### Задание 8. Синхронизация без merge-коммитов

1. Во втором клоне (из задания 3) сделайте коммит и запушьте.
2. В первом клоне сделайте другой коммит (в другом файле) и попробуйте `git push`. Почему отказ?
3. Выполните `git pull --rebase`, затем `git push`. Проверьте, что история линейная.
4. Повторите эксперимент с обычным `git pull` и сравните графы.

### Задание 9 (со звёздочкой)

- `git rebase -i HEAD~4`: склейте два коммита, переименуйте третий, поменяйте порядок.
- Разберитесь в отличии `git reset --soft`, `--mixed`, `--hard` на одном и том же коммите (делайте на резервной ветке).
- Настройте в `~/.gitconfig` алиас `lg` для `log --graph --decorate --oneline --all` и `pull.rebase = true`.
- Пройдите уровни по ветвлению на https://learngitbranching.js.org/.

## Критерии готовности

- Можете без подсказок пройти цикл `init → add → commit → remote add → push → pull`.
- Можете нарисовать граф после merge и после rebase для одной и той же пары веток.
- Умеете читать маркеры конфликта и разрешать конфликт любой из трёх стратегий.
- Понимаете, какие команды переписывают историю (`amend`, `rebase`, `reset`) и почему их не применяют к общим веткам.
