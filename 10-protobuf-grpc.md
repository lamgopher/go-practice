## Вопросы для самопроверки

1. Какие две проблемы JSON решает protobuf? Чем приходится платить?
2. Зачем каждому полю номер? Что именно попадает в бинарное сообщение — имя поля или номер?
3. Как объявить массив, словарь, перечисление, «одно из нескольких»? Какие типы не могут быть ключом map?
4. Почему `oneof` при установке второго поля затирает первое?
5. Какие проблемы «голого» `protoc` решает `buf`?
6. Что вернёт `msg.GetItems()[0].GetParams()["missing"].GetDoubleValue()`, если ключа нет? Почему цепочка не паникует?
   А где она всё-таки запаникует?
7. Почему в proto3 нельзя отличить отсутствующее скалярное поле от нулевого? Как эту проблему решают?
   (Уточните самостоятельно: что даёт ключевое слово `optional` в современных версиях proto3?)
8. Из каких двух частей состоит ключ поля в wire-формате? Назовите четыре используемых wire type.
9. Закодируйте число 300 как varint. Сколько байт займёт `int64` со значением 1? Со значением −1?
10. Как на проводе выглядит `repeated` поле сообщений? Почему одиночное поле можно превратить в `repeated`?
11. Перечислите безопасные и опасные изменения схемы. Зачем `reserved`?
12. Что такое RPC? Что даёт HTTP/2 для gRPC?
13. Из чего складывается полное имя gRPC-метода и почему нельзя переименовать пакет, сервис или метод?
14. Зачем сгенерированный клиент выносят в отдельный Go-модуль?
15. Что такое метаданные gRPC и для чего их используют?
16. Как вернуть ошибку с кодом и как разобрать её на клиенте? Чему примерно соответствуют `InvalidArgument`,
    `NotFound`, `Internal`, `DeadlineExceeded` в HTTP?

18. Какие бывают виды стриминга?

## Практика

Инструменты: `buf`, `protoc-gen-go`, `protoc-gen-go-grpc`, `grpcurl` (или Postman/Evans вместо BloomRPC из лекции).

### Задание 1. Схема

Опишите `api/catalog/v1/catalog.proto`:

- `Product`: `id` (uint64), `title`, `price` (int64, копейки), `tags` (repeated string), `attributes`
  (`map<string, AttributeValue>`), `status` (enum с нулевым значением `STATUS_UNSPECIFIED`), `created_at`
  (`google.protobuf.Timestamp`), `description` (должно различаться «не задано» и «пустая строка»);
- `AttributeValue` с `oneof value { double, int64, bool, string }`;
- сообщения запросов/ответов и сервис с методами `CreateProduct`, `DescribeProduct`, `ListProducts`, `RemoveProduct`.

Настройте `buf.yaml` (lint + breaking) и `buf.gen.yaml`; добейтесь чистого `buf lint`.

### Задание 2. Сериализация вручную

1. Заполните `Product`, сериализуйте `proto.Marshal`, выведите байты в hex. Сравните размер с `json.Marshal` той же
   структуры и с `protojson.Marshal`.
2. Разберите hex вручную по правилам wire-формата для сообщения `{id: 150, title: "go"}`: найдите ключи, wire type,
   varint и длину строки. Проверьте себя командой `protoc --decode_raw`.
3. Напишите на Go функции `EncodeVarint(uint64) []byte` и `DecodeVarint([]byte) (uint64, int)` с табличными тестами
   (0, 1, 127, 128, 300, max uint64).
4. Проверьте поведение геттеров: цепочка вызовов на nil-сообщении; обращение по индексу к пустому `repeated`.
5. Кросс-языковая проверка, как в демо: сериализуйте сообщение из Python (или через `buf convert`/`protoc --encode`)
   и прочитайте в Go.

### Задание 3. Эволюция схемы

Сохраните бинарный файл сообщения «версии 1» и последовательно меняйте схему, каждый раз читая старый файл новым
кодом и новый файл старым кодом:

1. добавьте поле;
2. удалите поле и поставьте `reserved`;
3. поменяйте `int32` на `int64`; затем `int64` на `string` (что будет?);
4. превратите одиночное вложенное сообщение в `repeated` и обратно;
5. переиспользуйте номер удалённого поля под другой тип (чтобы увидеть, почему так нельзя);
6. переименуйте поле, не меняя номер.

Запускайте `buf breaking --against` и сверяйте его вердикт со своими наблюдениями. Оформите таблицу
«изменение → безопасно для бинарного формата? → безопасно для JSON? → ломает сгенерированный код?».

### Задание 4. gRPC-сервер и клиент

1. Реализуйте сервис из задания 1 с хранением в памяти (потокобезопасно). Встраивайте `UnimplementedXxxServer`.
2. Ошибки: `InvalidArgument` для невалидного запроса, `NotFound` для отсутствующего товара, `Internal` — без утечки деталей.
3. Проверьте `grpcurl` (включите reflection): список сервисов, вызовы методов.
4. CLI-клиент: соединение, вызов с контекстом и таймаутом, разбор ошибки через `status.FromError` с ветвлением по коду.
5. Тесты сервера без сети — через `google.golang.org/grpc/test/bufconn`.
6. Вынесите сгенерированный код в `pkg/catalog` с собственным `go.mod`; в корневом модуле подключите через `replace`.
   Убедитесь, что клиентский модуль не тянет зависимости сервера (`go mod graph`).

### Задание 5. Метаданные и интерсепторы

1. Клиент передаёт `x-request-id` и `authorization` в метаданных; сервер читает их.
2. Серверные unary-интерсепторы, подключённые цепочкой: логирование (метод, длительность, код); recovery
   (паника → `Internal`); валидация (если запрос реализует `interface{ Validate() error }` → `InvalidArgument`);
   проверка токена (`Unauthenticated`).
3. Клиентский интерсептор, добавляющий `x-request-id` в каждый вызов.
4. Проверьте порядок выполнения цепочки логами. Что будет, если recovery поставить последним?

### Задание 6. Дедлайны

1. Метод сервера «работает» 2 с и уважает `ctx.Done()`. Клиент вызывает с дедлайном 500 мс: какой код получит клиент
   и что увидит сервер?
2. Цепочка A → B → C: убедитесь, что дедлайн распространяется по цепочке сам. Что будет, если B вызовет C с
   `context.Background()`?

### Задание 7. Стриминг

1. Server-streaming `WatchProducts`: сервер присылает событие при каждом создании/удалении товара.
2. Client-streaming `ImportProducts`: клиент шлёт товары потоком, сервер отвечает количеством созданных.
3. Корректное завершение при отмене контекста клиентом; отсутствие утечки горутин на сервере.

### Задание 8. grpc-gateway

1. Добавьте `option (google.api.http)` для всех методов (`GET /v1/products/{id}`, `POST /v1/products` с `body: "*"`
   и т. д.), сгенерируйте gateway и OpenAPI.
2. Поднимите gRPC и HTTP на разных портах в одном процессе; общий graceful shutdown.
3. Проверьте `curl`: успех, невалидный запрос (какой HTTP-код?), несуществующий товар.
4. Пробросьте HTTP-заголовок `X-Request-Id` в метаданные gRPC.

## Критерии готовности

- Читаете hex-дамп небольшого protobuf-сообщения без инструментов.
- По памяти называете пять правил безопасной эволюции схемы.
- Сервис возвращает осмысленные коды ошибок, клиент ветвится по ним, всё покрыто тестами на `bufconn`.
- Понимаете, какие части пути `/package.Service/Method` нельзя трогать после релиза.
