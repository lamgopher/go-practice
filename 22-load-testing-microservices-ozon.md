## Практика

### Часть A. Нагрузочное тестирование

Объект: `product-service` + `category-service` + PostgreSQL из прошлых занятий, со включёнными метриками и
трейсами. Инструменты на выбор: `k6`, `vegeta`, `ghz` (gRPC), Yandex.Tank/Pandora (ближе всего к лекции).

#### A1. Первая стрельба

1. Сценарий чтения (`GetProduct` по случайному id из заранее загруженного миллиона): постоянная нагрузка 100 RPS, 2 минуты.
2. Разберите отчёт: RPS фактический и заданный, p50/p90/p99/max, доля ошибок по кодам.
3. Сопоставьте с дашбордом сервиса (занятие 16): совпадают ли перцентили у генератора и у сервиса? Почему могут не совпадать?

#### A2. Поиск предела

1. Линейный рост от 0 до N RPS за 5 минут (N подберите так, чтобы сервис «сломался»).
2. Определите точку деградации: RPS, на котором p99 превысил SLO (например 300 мс) или появились ошибки.
3. Найдите узкое место по метрикам, трейсам и pprof: CPU сервиса, пул соединений, база, зависимый сервис.
4. Устраните одно узкое место (индекс, размер пула, кеш, лимиты) и повторите. Запишите «было / стало».
5. Сравните закрытую модель (50 виртуальных пользователей) с открытой на том же сервисе: как выглядит перегрузка в каждой?

#### A3. Запись и смешанный профиль

1. Сценарий записи (`CreateProduct`) с тестовыми данными, помеченными признаком `is_test`; очистка после теста.
2. Смешанный профиль 90% чтения / 10% записи. Как запись влияет на латентность чтения?
3. Проверьте, что нагрузка не «утекает» в зависимости сверх ожидаемого (RPS в `category-service`, записи в Kafka).

#### A4. Кеш и холодный старт

1. Добавьте кеш (Redis) для чтения товара с TTL 3 минуты (домашнее задание курса, п. 5).
2. Три стрельбы: без кеша, с холодным кешем, с прогретым. Сравните графики.
3. Отключите Redis во время стрельбы: сервис обязан продолжить работу (медленнее), а не начать отдавать ошибки.
4. «Набег»: одновременное истечение TTL у популярных ключей — что с базой? Смягчите (jitter TTL, singleflight).

#### A5. Стресс, стабильность, защита

1. Стресс: 2–3× от предела на 2 минуты, затем возврат к норме. Восстановился ли сервис сам? За сколько?
2. Soak: 50% от предела на 30–60 минут. Растут ли память, число горутин, lag?
3. Защита от перегрузки: ограничение одновременных запросов (семафор/интерсептор) с ответом `ResourceExhausted`,
   таймауты, circuit breaker на вызов `category-service`. Повторите стресс-тест и сравните.
4. Автоматизация: порог «p99 < X и ошибок < Y%» как критерий прохождения теста в CI.

### Часть B. «Стандарт микросервиса»

Проведите аудит своих сервисов по чек-листу лекции и доведите до соответствия.

| # | Требование | Как проверить |
|---|------------|---------------|
| 1 | Имя сервиса в kebab-case, единое в логах, метриках, трейсах | grep по конфигам и дашбордам |
| 2 | Наружу HTTP/JSON, внутри gRPC; время в RFC 3339 / UTC | контракты |
| 3 | В proto указаны `package` и `go_package` | `buf lint` |
| 4 | Служебный порт: `/live`, `/ready`, `/version`, `/metrics`, `/debug/pprof`, swagger | `curl` |
| 5 | Readiness не зависит от внешних сервисов; `false` после `SIGTERM` и до окончания прогрева | эксперимент |
| 6 | Graceful shutdown всех компонентов с таймаутом | `kill -TERM` под нагрузкой — без ошибок у клиента |
| 7 | Логи: JSON в stdout, есть `message`, уровень, `trace_id` | вывод |
| 8 | Метрики RPS/RT/ошибок для входящих и исходящих вызовов, БД, кеша; build info | `/metrics` |
| 9 | Секретов нет в репозитории и образе | `gitleaks`, просмотр |
| 10 | Конфиг: статический + изменяемые на лету параметры (таймауты, размеры батчей) | смена без рестарта |
| 11 | Сервис работает при недоступном кеше; некритичные зависимости деградируют мягко | отключить зависимость |
| 12 | Один процесс в контейнере, entrypoint — бинарник сервиса | Dockerfile |
| 13 | Линтеры, `goimports`, сгенерированный код закоммичен (`make generate` не даёт diff) | CI |
| 14 | Миграции обратно совместимы с предыдущей версией кода | прогон старого кода на новой схеме |

Отдельные упражнения:

1. **Пробы.** Реализуйте `/live` и `/ready`. Смоделируйте ошибку: readiness проверяет `category-service`; отключите
   его и опишите, что произошло бы в Kubernetes с обоими сервисами. Исправьте.
2. **Realtime-конфиг.** Таймаут вызова `category-service` меняется без перезапуска: файл с перечитыванием по
   сигналу либо etcd/Consul с watch. Доступ к значению — через функцию, а не глобальную переменную.
3. **Канарейка локально.** Две версии сервиса за nginx/Envoy/Traefik с весами 100/0 → 90/10 → 50/50 → 0/100;
   попадание на новую версию по заголовку при весе 0. Сравнивайте метрики версий по лейблу `version`.
4. **Миграция в три релиза.** Переименование колонки без простоя: (1) добавить новую и писать в обе; (2) перенести
   данные и читать из новой; (3) удалить старую. На каждом шаге проверяйте откат кода на предыдущую версию.
5. **Повторные попытки** (домашнее задание курса, п. 4): ретраи с экспоненциальной задержкой и jitter для
   подключения к базе, вызова соседнего сервиса и отправки в Kafka. Какие ошибки нельзя повторять? Как не устроить
   «шторм ретраев» при падении зависимости?
6. **Хотфикс или откат.** Опишите регламент для своей системы: когда откатываем, когда катим хотфикс, кто
   подтверждает, какие проверки обязательны.

### Часть C. Итоговый проект курса (task-7)

Сведите всё вместе по `materials/task-7.md`:

1. Ретранслятор — отдельный бинарник (`cmd/retranslator`) и отдельный контейнер.
2. Telegram-бот (занятие 05) ходит в API-сервис по gRPC вместо dummy-сервиса.
3. Чтение списков бот берёт из сервиса-фасада.

Kafka → фасад → его база → чтение ботом. Один трейс на всю цепочку, дашборд, алерты, нагрузочный тест с отчётом.
