## Вопросы для самопроверки

1. Какие задачи решает кеш? Какой минимальный набор методов ему нужен?
2. Зачем объявлять ошибку «не найдено» переменной пакета, а не создавать её каждый раз?
3. Что произойдёт с кешем на голой map при конкурентном доступе — потеря данных или что-то ещё?
4. Какие аргументы прозвучали за возврат интерфейса из конструктора и какие против (вспомните занятие 04)?
5. Чем вспомогательная функция нагрузки для тестов отличается от такой же для бенчмарков? Почему?
6. Почему при равной доле чтений и записей `RWMutex` проиграл `Mutex`, а при 90% чтений — выиграл?
7. Какой мьютекс выбирать по умолчанию, если профиль нагрузки неизвестен?
8. Что даёт встраивание интерфейсов на примере `CacheWithMetrics`?
9. Почему бенчмарк «int под мьютексом против atomic» давал то один, то другой результат? Что это говорит о
   микробенчмарках?
10. Как устроен `context.WithTimeout`? Что возвращает `ctx.Done()`? Зачем вызывать `cancel`, если таймаут и так истечёт?
11. Почему нельзя в `select` просто вызвать долгую функцию в `default` и надеяться, что `ctx.Done()` её прервёт?
12. В асинхронной обёртке вызывающий ушёл по таймауту. Что будет с горутиной, которая после этого пишет результат в
    небуферизованный канал? Как это исправить?
13. Может ли контекст принудительно остановить выполняющуюся функцию?
14. Какой ценой достаётся кеш «без мьютексов» на горутине-владельце?
15. Что вернёт операция чтения из канала, который закрыли, не записав ничего?
16. В ретрансляторе из домашнего задания: кто консьюмер, а кто продюсер и с чьей точки зрения? Зачем `Lock`/`Unlock`
    у `EventRepo`? Что такое at-least-once и почему его нет в наивной реализации?

## Практика

### Задание 1. Кеш с нуля (20 минут по таймеру, как на воркшопе)

```go
var ErrNotFound = errors.New("key not found")

type Cache interface {
    Set(key, value string) error
    Get(key string) (string, error)
    Delete(key string) error
}
```

Напишите реализацию, не подглядывая в прошлые занятия. Затем самопроверка по чек-листу разбора: защита от гонок,
`defer Unlock`, какой блокировкой закрыт `Get`, что возвращает `Get` для отсутствующего ключа, что возвращает конструктор.

### Задание 2. Тестовая обвязка

1. `TestCache`: записали → прочитали; перезаписали → прочитали новое; удалили → `ErrNotFound`; удаление
   несуществующего ключа.
2. Вспомогательная `emulateLoad(t *testing.T, c Cache, parallelFactor int)`: три группы горутин (set/get/delete) с
   уникальными ключами; `Get` допускает только `nil` или `ErrNotFound`.
3. Прогоните один и тот же набор тестов по всем реализациям (v1 без мьютекса, `Mutex`, `RWMutex`) через табличный
   тест с фабриками `func() Cache`. v1 должна падать; запустите всё с `-race`.

### Задание 3. Бенчмарки с двумя профилями

1. `emulateLoadBench(c Cache, parallelFactor int)` — без `testing.T`, без логов; неожиданная ошибка → `panic`.
2. Вариант «чтений в 10 раз больше записей».
3. Таблица результатов `Mutex` против `RWMutex` для обоих профилей при `parallelFactor` = 100, 1000, 10000.
   Используйте `-count=10` и `benchstat`. Сходится ли с цифрами воркшопа (64 против 43 и 147 против 166)?
4. Добавьте шардированную реализацию и `sync.Map`. Кто выигрывает в каждом профиле?

### Задание 4. Метрики

1. Объявите `Metrics { TotalAmount() int64 }` и `CacheWithMetrics`, встраивающий оба интерфейса.
2. Две реализации счётчика: поле `int64` под тем же мьютексом и `atomic.Int64`.
3. Тест: после N `Set` уникальных ключей и M `Delete` счётчик равен N−M. Не забудьте, что `Set` существующего ключа и
   `Delete` отсутствующего не должны менять счётчик (в коде воркшопа была «небольшая недоработка» — найдите похожую у себя).
4. Бенчмарк обоих вариантов, 10 прогонов. Оцените разброс и сделайте вывод о значимости разницы.

### Задание 5. Контекст и таймауты

Оберните «медленный» кеш (каждая операция спит 2 мс) в асинхронный:

```go
type AsyncCache interface {
    Set(ctx context.Context, key, value string) error
    Get(ctx context.Context, key string) (string, error)
    Delete(ctx context.Context, key string) error
}
```

1. Реализуйте через горутину + канал результата + `select` с `ctx.Done()`; при таймауте возвращайте `ctx.Err()`.
2. Тесты: таймаут 1 мс → `context.DeadlineExceeded`; таймаут 3 мс → успех; ручной `cancel()` до вызова → `context.Canceled`.
3. **Утечка.** Сделайте канал результата небуферизованным, вызовите `Get` 1000 раз с таймаутом 1 мс, подождите
   секунду и выведите `runtime.NumGoroutine()`. Затем сделайте буфер 1 и повторите. Объясните разницу. (На воркшопе
   этот эксперимент сначала «не воспроизвёлся» — разберитесь почему и добейтесь воспроизведения.)
4. Ответьте: после таймаута `Set` значение в кеше есть или нет? Как это задокументировать для пользователя API?
5. Добавьте в сам «медленный» кеш поддержку контекста, чтобы работа реально прерывалась, а не просто игнорировался
   результат.

### Задание 6. Кеш на горутине-владельце

Реализуйте кеш без мьютексов: одна горутина владеет map и обслуживает запросы из канала команд

1. Методы `Run(ctx)`, `Set`, `Get`, `Delete`; корректная остановка по контексту.
2. Прогоните тесты и бенчмарки из заданий 2–3. Сравните с мьютексами и объясните результат.
3. Назовите сценарий, где такой дизайн всё же оправдан.

### Задание 7. TTL и вытеснение (расширение)

1. Добавьте `SetWithTTL(key, value, ttl)`; просроченные записи не возвращаются и удаляются фоновой горутиной

## Критерии готовности

- Кеш, тесты и бенчмарки пишутся без подсказок за разумное время.
- Можете показать цифрами, когда `RWMutex` полезен, а когда вреден.
- Асинхронная обёртка не оставляет горутин после таймаута — подтверждено тестом.
- Можете нарисовать схему ретранслятора и показать на ней, где теряется или дублируется событие.
