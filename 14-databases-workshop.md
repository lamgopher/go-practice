## Практика

Продолжайте `product-service` и `category-service` из занятий 11–12.

### Задание 1. Контейнеризация

1. Multi-stage `Dockerfile` для каждого сервиса с правильным порядком слоёв. Измерьте время пересборки после
   правки одного `.go`-файла при «правильном» и «наивном» (`COPY . .` в начале) порядке.
2. Сравните размер образов: `golang`, `alpine`, `distroless`/`scratch` (со статической сборкой `CGO_ENABLED=0`).
3. `docker-compose.yml`: оба сервиса, PostgreSQL с томом и `healthcheck`, `depends_on` с `condition: service_healthy`.
4. `docker compose down` и `up` — данные на месте; `down -v` — данных нет. Объясните.

### Задание 2. Пакет подключения

1. `internal/pkg/db`: `NewPostgres(ctx, cfg Config) (*sqlx.DB, error)`, где `Config` — интерфейс с методами
   `GetDSN()`, `GetMaxOpenConns()`, `GetMaxIdleConns()`, `GetConnMaxIdleTime()`, `GetConnMaxLifetime()`.
2. Конфигурация из YAML с `time.Duration` и переопределением DSN переменной окружения (пароль не в репозитории).
3. В `main`: контекст запуска с таймаутом 1 мин, отдельный контекст для shutdown.
4. Миграции `goose` из приложения (`go:embed`), команда задаётся флагом (`up`, `status`, `down`).

### Задание 3. CRUD через squirrel + sqlx

Реализуйте репозиторий `product-service`: `SaveProduct` (с `RETURNING id`), `GetProducts(ids)`, `DeleteProducts(ids)`,
`UpdateProduct`. Добавьте gRPC-ручки с валидацией `repeated`-полей (`min_items`, каждый элемент `> 0`).

Чек-лист граблей с воркшопа — проверьте каждую у себя: распаковка `args...`; `PlaceholderFormat(sq.Dollar)`;
соответствие имён колонок тегам `db`; возврат результата из функции (а не только из запроса); пустой список id.

### Задание 4. JSONB-колонка

4. Запрос «товары, у которых атрибут `color` = `red`» оператором `@>` и GIN-индекс. Вспомните предостережения из

### Задание 5. Транзакции

1. Хелпер `WithTx(ctx, db, opts, fn)`: `Commit` при `nil`, `Rollback` при ошибке и при панике (с повторной паникой).
2. Методы репозитория принимают `sqlx.ExtContext` (или пару `QueryerContext`/`ExecerContext`), чтобы работать и с
   базой, и с транзакцией.
3. Бизнес-операция: «создать товар и записать событие о создании» в одной транзакции (заготовка outbox).
4. Тест: ошибка на втором шаге откатывает первый.
5. Альтернативный дизайн: транзакция в контексте (`ctx` → `tx`). Сравните оба подхода по явности и удобству.

### Задание 7. CTE и EXISTS

### Задание 9. Распределённая блокировка

1. Функции `TryLock(ctx, tx, lockType, id) (bool, error)` и `Lock(ctx, tx, lockType, id) error` поверх

3. Реализуйте то же через `SELECT ... FOR UPDATE SKIP LOCKED` по таблице задач и сравните подходы.

### Задание 10. Домашнее задание курса (task-4): Transactional Outbox

3. `EventRepo`: `Lock(n)` — атомарно взять `n` необработанных событий и пометить заблокированными (напишите два

   `Unlock(ids)`; `Remove(ids)`.
4. Проверка: запустите 5 параллельных `Lock(100)` на 500 событиях — множества не должны пересекаться.
5. Подключите ретранслятор из занятия 08 к настоящему `EventRepo`.
6. Со звёздочкой: партицирование таблицы событий по хешу `package_id` на N частей; датасет на миллион строк;
   несколько типов событий обновления.

## Критерии готовности

- `docker compose up` поднимает всю систему с нуля, включая миграции.
- Бизнес-изменение и событие о нём записываются атомарно; параллельные `Lock` не выдают одно событие дважды.
- Репозиторий одинаково работает с базой и с транзакцией.
- Фоновые задачи не обрываются вместе с запросом и не теряются при остановке.
